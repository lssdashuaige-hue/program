# PAS-024 — Scaling Architecture & Production Readiness

**中文名：** 规模化架构与正式上线准备
**版本：** 0.1

## 规模化目标

在用户增长时保持每个人仍被认真、安全地理解。规模化不能以降低探索质量、削弱隐私或扩大未经验证的自动化为代价。

## 主要挑战

- 长对话带来的模型成本；
- 持续增长的消息与记忆数据；
- 不同用户间的质量一致性；
- 风险检测和危机响应稳定性；
- 高敏感数据的访问与删除；
- 外部模型和云服务故障。

## 演进架构

Alpha 保持模块化单体。只有观测数据证明需要时，才拆分：

- Conversation service；
- Memory service；
- Safety service；
- AI orchestration；
- asynchronous summary jobs。

避免为假设流量提前引入微服务和复杂队列。

## 成本控制

- 只发送当前消息、必要上下文和少量相关记忆；
- 对旧对话进行用户可见的结构化总结；
- 简单分类使用低成本模型或确定性规则；
- 深度回应使用更强模型；
- 设置令牌、时间和重试上限；
- 监控每次探索成本，而非隐藏降级质量。

## 数据规模

- 为 `user_id`、会话时间和状态建立索引；
- 使用游标分页；
- embedding 与正文分离；
- 冷数据归档必须保持用户删除能力；
- 数据分区只在规模证据支持时采用；
- 定期运行安全和性能顾问。

## 稳定与安全

- API 限流与滥用防护；
- 幂等写入和请求 ID；
- 超时、熔断和安全降级；
- 数据库备份与恢复演练；
- Prompt、模型和策略可回滚；
- 生产密钥隔离；
- 不含心理正文的监控；
- 关键安全事件人工升级通道。

## 上线阶段

1. 内部测试 5～10 人；
2. Alpha 50～200 人；
3. Beta 1,000～5,000 人；
4. 通过安全、隐私、稳定和价值门槛后正式发布。

## Production Checklist

- 前后端自动化测试和端到端验证；
- RLS 与跨用户隔离测试；
- 危机与依赖评测；
- 删除、导出和同意撤回；
- 错误监控与告警；
- 隐私政策、服务边界和支持渠道；
- 成本上限和容量计划；
- 回滚和事故响应流程。
